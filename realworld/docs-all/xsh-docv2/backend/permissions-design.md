# 角色/权限表与中间件设计

本文档描述 v2 中角色、权限与中间件的设计，与 [02-auth-and-permissions.md](../02-auth-and-permissions.md) 配套使用。

---

## 一、角色定义

| 角色 | 标识（建议） | 说明 |
|------|--------------|------|
| 运营 | `operator` | 选品、内容、发布任务、评论等常规操作；不可绑定/解绑平台账号、不可管理用户与角色。 |
| 管理员 | `admin` | 拥有运营全部权限，并可绑定/解绑平台账号、管理用户与角色（若实现对应接口）。 |

与 [xsh-docs/01-overview](../../xsh-docs/01-overview.md) 中角色约定一致。

---

## 二、存储方案

- **方案 A（简单）**：在 `users` 表增加字段 `role`，取值如 `operator`、`admin`；默认新用户为 `operator`。
- **方案 B**：独立表 `user_roles`（user_id, role），支持一用户多角色时扩展。
- v2 建议采用 **方案 A**，在 [database/schema-v2-changes.md](../database/schema-v2-changes.md) 中与表结构统一。

---

## 三、权限点与 API 映射

以下为「需按角色限制」的典型接口；其余 xsh 接口在通过 JWT 后即可访问（即运营与管理员的权限一致）。

| 权限点 | 所需角色 | 涉及接口（示例） |
|--------|----------|------------------|
| 绑定/解绑平台账号 | admin | BindAccount、UnbindAccount（或等效的账号绑定/解绑 RPC） |
| 管理用户/角色（若实现） | admin | 用户列表、修改角色、禁用等 |

- 实现方式：在 JWT 之后增加权限中间件，按路由或 RPC 方法名判断所需角色；从 context 读取 `role`，不满足则返回 403。
- 若后续权限点增多，可引入「权限码」与「角色-权限」映射表，本阶段可仅按角色判断即可。

---

## 四、中间件顺序

1. **JWT 中间件**：校验 Token，解析 `user_id`、`username`、`role` 写入 context。
2. **权限中间件**（可选）：对「仅 admin」等路由检查 context 中的 `role`，不满足则 403。

---

## 五、前端配合

- GetProfile（或扩展接口）返回当前用户 `role`，前端据此隐藏或禁用「绑定/解绑账号」等仅管理员可用的菜单或按钮。
- 后端仍须做权限校验，前端仅做展示与交互优化。
